# Plan Implementation

План читают владелец (утверждает по Scope) и агент (исполняет по Changes). Один текст.

Писать по-русски. Короткие полные предложения: есть подлежащее и сказуемое. Не эссе и не телеграф.

## Before writing

1. Прочитать [`docs/adr/README.md`](../../../docs/adr/README.md).
   Если правка в зоне Gate trigger или конфликтует с `do-not` —
   план = показать ADR (id, do-not, цена, Reopen), **без шагов кода**,
   пока владелец не сказал `supersede ADR-N` в этом сеансе.
2. Найти существующий код; указать paths, которые reuse.
3. Scope — эффект для пользователя или продукта. Секция Out of scope не обязательна; писать её только по тесту забора ниже.
4. `catalog.json` и `NOTES.md` руками не править — только через
   `scripts/build_catalog.py` (`NAME_OVERRIDES`, `AEMET_FORCE_PAIRS`,
   `AEMET_REJECT_REASONS`, `FORCE_CONCELLO`, `COORD_OVERRIDES`).
5. План правок `index.html` или UI не переименовывает события `track` (комментарий у `track` в [`index.html`](../../../index.html)). Новые значения полей внутри события можно. `PRIMARY_ORDER` и `pick_primary` выбирают только суточное `beach.t`; волны, ветер и `score` в этот кортеж не входят — [AGENTS.md](../../../AGENTS.md) (On ADR, plans, and reports) и [docs/adr/README.md](../../../docs/adr/README.md) п.9.

Неясный запрос (нет дефекта / цели / ограничения) — спросить, не угадывать.

## How to write

Читатели: владелец и агент. «Concise» в Cursor не разрешает телеграф.

Каждая строка Goal, Scope, Changes и overview: подлежащее и сказуемое. Одна мысль — одна строка. Независимая мысль — то, что можно отдельно проверить в Done.

Запрещено в Goal, Scope и Changes (тот же критерий, что у `/analyse-plan`):
- ярлык вместо фразы (`Лицо:`, `Оборот:`)
- несколько независимых требований через `;` или «потом» или запятой, кроме запятой внутри одного скопированного отрезка `**…**`
- фраза без глагола
- словосочетание P в Scope: в блоке Changes, который этот пункт забирает по обходу ниже, есть предложение, которое начинается стартером `Это ` / `это ` / `А именно` / `а именно` / `Имеется в виду` / `имеется в виду`, сразу перед ним стоит предложение, P входит в это предыдущее предложение и не входит в перечисление после стартера; перечисление после стартера — два и более имён

Разрешено:
- маркированный список
- путь и символ в Changes в той же фразе: «На обороте таблицы сразу, без `<details>` (`cardBackHtml`).»

**Goal** — одно полное предложение исхода для пользователя. Не склад фич. Ограничения — отдельные буллеты в Changes, не второе предложение Goal.

**Scope** — для владельца. Полные простые предложения. Что станет иначе на экране или в продукте. Без пути к файлу и без токена в backticks. Слово без backticks и без пути к файлу — не символ. URL и строка со слэшем, которая не путь к файлу, — не символ. Владелец утверждает план по Scope, не читая Changes.

**Changes** — для агента. Путь, символ, что меняется. Не копировать фразу Scope. Один общий список запрещён: Changes режется на блоки. Сопоставление с пунктами Scope — обход в «Блоки Changes».

Не писать «почему» (аудит, эвристики, история бага), пока владелец не попросил. Не дублировать Goal в overview, Approach и Changes.

`/analyse-plan` помечает телеграф в Goal, Scope и Changes. YAML todos этим правилом не покрыты.

### Scope и Changes не дублируют друг друга

Пункт Scope проверяется без открытия файла. Пункт Changes называет путь.

Если в Scope есть путь или символ, механизм уходит в Changes, а Scope переписывается как эффект. Changes без пути, который только пересказывает Scope, удаляется или получает путь.

Плохо: в Scope «`mapsQuery` по `lat,lon`», в Changes плоский список с тем же.

Хорошо: в Scope «Кнопка Карта открывает точку на карте, а не поиск по названию». В Changes блок про Карту: «В `index.html` `mapsQuery` берёт координаты из `index.geo`».

Пример телеграфа. Было:

> Клик не меняет высоту ряда. Лицо: °C, потом индекс с видимой меткой и тултипом. Оборот: шкалы хорошо/плохо без цифр; таблицы истории сразу, скролл без полосы.

Стало:

- Клик по карточке переворачивает её. Высота ряда не меняется.
- На лице слева температура в °C. Справа индекс с видимой подписью и тултипом (тач, не только hover).
- На обороте части индекса — шкалы «хорошо / плохо» без цифр. Таблицы истории видны сразу. Скролл внутри карточки, полоса скрыта.

### Блоки Changes

Идти сверху вниз по блокам Changes и сверху вниз по пунктам Scope. Блок без абзаца с начала `**` забирает ровно один следующий пункт Scope. Блок с N абзацами с начала `**` забирает следующие N пунктов Scope, если они уже содержат эти отрезки в том же порядке. Иначе этот блок забирает ровно один следующий пункт Scope. Другого сопоставления нет. После полного обхода пунктов Scope не должно остаться, и каждый пункт забран ровно одним блоком. Заголовок блока — номер или короткая метка, не копия фразы Scope. Пункт Changes без своего блока Scope запрещён. Пустой блок запрещён: либо дописать Changes, либо убрать пункт Scope. Общая правка на несколько эффектов живёт в блоке того пункта Scope, без которого она не нужна.

### Out of scope (необязательный забор)

Секцию писать только если есть хотя бы один пункт, для которого верны все три условия. Каждое условие проверяется по тексту плана, канона и названного файла. Оценку вероятности не писать.

1. Пункт называет символ из файла, который уже есть в Changes, или формулировку из запроса владельца, и этого нет в Goal и нет в Changes.
2. Этого запрета нет в [`AGENTS.md`](../../../AGENTS.md), в [`docs/adr/README.md`](../../../docs/adr/README.md) и в Changes.
3. Пункт называет путь или символ, которого ещё нет строкой в Blast radius.

Если ни один пункт не проходит тест, секцию Out of scope не писать. Пустой заголовок не оставлять.

Пример забора: в плане про комфорт на прогноз не кладём почасовой ряд в JSON. Пример забора: не строим Google Directions, если Changes говорят только про точку на карте.

Не писать шум, который уже стоит в каноне или в другом плане: не переименовывать `track`; не править `catalog.json` руками; не трогать CMEMS в UI-плане; не делать работу из соседнего плана.

## Plan shape (только нужные секции)

1. **Goal** — одно полное предложение: что станет правдой для пользователя. Не склад фич. Ограничения — отдельные буллеты в Changes.
2. **Scope** — эффект для владельца, без пути к файлу и без токена в backticks. Out of scope только по тесту забора.
3. **Approach** — один; варианты только если без выбора нельзя продолжить.
4. **Changes** — блоки по пунктам Scope; в каждом блоке path + символ + что меняется (reuse vs new).
5. **Steps** — нумерация только если важен порядок.
6. **Blast radius** — правило ниже.
7. **Done** — как проверить конкретно.
8. **Open questions** — только блокеры; иначе секцию не писать.

Утверждения «существует / вызывается / меняем X» — только после grep/чтения
кода (path, символ). Иначе не писать или пометить как assumption.
Goal и Scope от пользователя проверять кодом не нужно.

Если план уже несёт `## Review ledger` или `## Deferred choices`, автор их не сокращает и не удаляет. Сам автор эти секции не создаёт, их пишет петля ревью, когда она доступна. `Out of scope` — чего не делаем по тесту забора. `Open questions` — блокеры для владельца. `Deferred choices` — применённые дефолты ASK, писать вручную нельзя.

Перед повторной выдачей плана: `rg -n '^## (Review ledger|Deferred choices)' <plan.md>`. Если совпадение есть, правится этот файл, а новый файл плана не создаётся.

## Blast radius

Найти **реальных потребителей** места правки. Для каждого: guard in scope
или явный out-of-scope риск. Не выдумывать empty/loading/validation,
если это не следует из потребителя.

Цепочка репо (идти по ней, не по каталогу гипотез):

| Меняем | Потребители |
| --- | --- |
| `scripts/build_catalog.py` / поля каталога | `catalog.json` → `scripts/update_beaches.py` |
| `scripts/update_beaches.py` (логика/выход) | `write_data_split`, `run_selfcheck`, `data/*.json`, `index.html`, `.github/workflows/update-beaches.yml` |
| форма `data/index.json` / `data/<slug>.json` | `index.html`: `fetchedAt`, `concellos`, `beachConcello`, `top`; у пляжа `t`, `source`, `trend`, `sources` |
| только `index.html` | depth-1 callers в `index.html`, включая другие функции того же файла; поля data не выдумывать |
| workflow / флаги bake | README cron, `--skip-copernicus`, secrets |
| символы Gate trigger в ADR | не кодить — см. Before writing |

Локальная правка без других потребителей — одна строка (`low risk: …`).
Много потребителей — группировать по флоу, сценарий не выкидывать.

При записи заголовка: для каждого символа, который план называет, и для каждого
экспорта файла правки — grep вызывающих и импортёров, depth 1, только
зависимость от контракта (сигнатура, семантика, форма выхода, формат хранения).
Вызывающий в том же файле — отдельный символ в строке `path:`. Строка
`index.html: sortBeaches` не закрывает `nearbyBeaches`. Вызывающих у
caller-only строк не грепать.

## Done

Без чеклиста «на всякий случай». Только то, что закрывает Goal.

- Логика bake (`pick_primary`, `merge_history`, `attach_primary_fields`, split):
  `python3 scripts/update_beaches.py --selfcheck`.
- Каталог: `python3 scripts/build_catalog.py` — только если rebuild входит в Changes.
- UI: какое поле/состояние в `index.html` должно отличаться.

Новый тестовый раннер не предлагать. Расширять `run_selfcheck` — только если
без этого конкретный сценарий отъедет незаметно; иначе `run_selfcheck` не расширять.

## Self-check

- Исполнитель может сделать работу по paths и steps.
- Нет пропущенного потребителя.
- Нет шагов, без которых Goal всё равно выполняется → убрать.
- Один подход.
- ADR не нарушен (или план — показ конфликта, не код).
- Владелец понимает Goal без чата.
- Владелец понимает Scope без Changes.
- В Scope нет пути к файлу и нет токена в backticks.
- Changes не пересказывает Scope.
- Обход блоков Changes и пунктов Scope сходится: каждый пункт забран ровно одним блоком, пунктов не осталось.
- Нет P по правилу подставки в списке «Запрещено».
- Каждый абзац Changes с начала `**X**` имеет пункт Scope с подстрокой X.
- В Goal, Scope и Changes нет телеграфа (ярлык вместо фразы, `;` / «потом» / запятая между требованиями, нет глагола).
- Каждый пункт Out of scope проходит три условия забора по тексту, без оценки вероятности. Если ни один не проходит, секции нет.
- Нет непрошеного «почему».
- План не переименовывает события `track`.
